Windows Detection Engineering with Wazuh & Atomic Red Team

A home-lab project covering the full path from attacker simulation to a tuned detection: running an Atomic Red Team technique against a Windows host, tracing it through endpoint telemetry, evaluating Wazuh's default detection, and writing custom rules to reduce false positives and improve alert fidelity.

Scope

The goal was to practice detection engineering, not just SIEM deployment — taking a default rule match and improving it based on an actual false-positive analysis, rather than treating an alert firing as the end state.

Scope of the project:

Run one Atomic Red Team technique against a Windows 11 host
Trace that activity through Sysmon and Windows Event Viewer, before ever looking at Wazuh
Confirm how Wazuh's default rule set handles it
Find the false positive that came from the test harness itself, not from the technique
Write a Wazuh rule to suppress that false positive without weakening detection
Write a second rule that reliably catches the actual technique regardless of how it's invoked
Document the before/after

The scope is deliberately one technique, covered end to end, rather than multiple techniques covered superficially.

The technique

MITRE ATT&CK: T1059.001 — Command and Scripting Interpreter: PowerShell Atomic test: T1059.001-15 — PowerShell executed via -EncodedCommand

I picked this one because it's simple enough to reason about end-to-end but still touches a behavior real attackers use constantly (Base64-encoded PowerShell to dodge basic string matching / logging). It's a good technique to learn detection tuning on because the "bad" signal (an encoded command) and the "noise" (test-harness artifacts) are easy to tell apart once you actually look at the telemetry instead of trusting the alert name.

What actually happened, step by step

1. Ran the atomic test on the Windows host. The test executed powershell.exe with -EncodedCommand, using a Base64/UTF-16LE encoded payload — which is the standard way PowerShell expects that flag to be used. Test harness reported success.

2. Checked the raw telemetry before touching Wazuh. Sysmon logged the process creation (parent process, command line, PID, GUID). Windows PowerShell Operational and Security logs backed that up. Point of this step: confirm the activity was actually visible at the source, so if Wazuh missed something later I'd know whether it was a collection problem or a rule problem.

3. Let it hit Wazuh and checked the default rules. Wazuh's built-in rule set (e.g. rule 92027, PowerShell spawning PowerShell) did pick up related activity. So ingestion and baseline correlation were working. Good — but the alerts were generic and one of them was flagging something that wasn't actually the attack.

4. Found the false positive. The atomic test's own harness leaves behind an artifact (PScriptPolicyTest) as part of how it runs — not related to the technique itself. A default rule matched on it and generated an unrelated alert. Left unaddressed, that kind of noise reduces the signal-to-noise ratio of the alert queue, so it was treated as something to fix rather than ignore.

5. Wrote two custom rules.

Rule 100201 — suppresses the known-benign PScriptPolicyTest artifact from the test harness. Scoped narrowly to that filename, not a blanket suppression of PowerShell activity.
Rule 100210 — flags powershell.exe execution when the command line contains an encoded-command indicator (-enc, -e, -ec, -EncodedCommand), independent of parent process. Severity level 10, mapped to T1059.001.

6. Compared before and after. Before: a correct-but-generic detection plus one irrelevant alert competing for attention. After: the benign artifact is suppressed, and the encoded-PowerShell behavior generates a clear, higher-confidence alert that isn't dependent on what spawned it.

The two rules, briefly

100201 — false positive suppression Matches the PScriptPolicyTest artifact generated by the Atomic Red Team harness and drops it before it becomes alert noise. Does not touch any other PowerShell activity.

100210 — encoded PowerShell detection Fires when powershell.exe is executed with any of the common encoded-command flags. Doesn't care about parent process, so it still catches the behavior if it's launched from something other than a normal shell.
